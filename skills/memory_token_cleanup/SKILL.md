# メモリ・トークンダイエット

トリガー: ユーザーが「メモリ掃除して」「メモリ整理して」「トークン節約して」「メモリの棚卸しして」と言ったら、この手順で実行する。

## 目的
毎回の会話で読み込まれるメモリファイル（MEMORY.md、SOUL.md、USER.md、IDENTITY.md、AGENTS.md など）の文字数を減らし、トークン消費を抑えること。
ただし目的は「短くすること」自体ではありません。あなたの今後の行動が変わらない範囲で、読み込む量だけを減らすことが目的です。

## 大原則（3層の置き場所）
メモリの中身を、次の3層に分けて考えてください。
1. ホット層（毎回読むファイルに残す）：今の結論だけ。現在の既定・禁止・呼称・好み・未決事項・識別子（チャットID、ファイルパス、設定名など、連携先を特定するために必要なもの）。
2. ウォーム層（必要な時だけ読む場所へ移す）：特定の作業でだけ必要な手順書・長い仕様・プロンプト全文。移した先のファイルが実在することを確認してから、ホット層には「詳細は ○○ を参照」の1行だけを残すこと。実在しないファイルへの参照は作らないこと。
3. コールド層（普段は読まない場所へ移す）：経緯・証拠・旧版・思い出。日付つきログやアーカイブファイルに残し、起動時には読み込ませない。

## 安全ルール（絶対に守ること）
- いきなり本物のメモリを書き換えない。最初は必ずコピーの上で整理ドラフトを作り、数字と実例を見せてから、私の採用判断を待つこと。
- 私の承認なしに項目を削除しない。削除候補は一覧で提示し、理由を添えること。
- 矛盾を見つけても、勝手にどちらかへ寄せて直さない。両方の記述を並べて「判断待ち」として報告すること。私の未決事項を、整理のついでに潰さないこと。
- 安全に関わる留保（未検証・一次情報未確認・ライセンス条件など）は、短くしても本文に残すこと。
- 感情の重みがある項目（後悔、体調、人間関係の機微など）は圧縮率を抑え、「どう扱うべきか」の結論を明記すること。事務的に潰さないこと。
- 識別子は「長いから」という理由で削らない。削減は説明文の側で稼ぐこと。

## 手順
### ステップ0：監査
対象ファイルの文字数・行数を実測し（推測のトークン数は出さず、文字数ベースで報告すること）、セクション別・項目別の長さを出す。長い順に項目を並べ、重複・矛盾・期限切れ・変更履歴が本文の大半を占めている項目を洗い出す。

### ステップ1：分類
各項目を次のA〜Fに分類し、一覧表で提示する。
A. 履歴圧縮できる：変更の経緯が長く書かれているが、今の結論は短く言える
B. 参照化できる：詳細が別の正本ファイル（設定ファイル、手順書、目標ファイルなど）に既にある
C. 重複：同じ内容が複数箇所にある
D. 削除候補：上書き済み（superseded）、一時的な進捗、終わった作業の報告
E. 矛盾・判断待ち：記述同士が食い違っていて、私の判断が要る
F. 落とせない：呼称・禁止・既定・識別子・未決事項など、削るとあなたの行動が変わるもの

各項目には、この4つの質問で判定する。
1. これが無いと、今のあなたの行動が変わるか？
2. 特定の作業の時だけ必要か？ → 必要ならウォーム層へ
3. 証拠・思い出として残したいだけか？ → ならコールド層へ
4. もう上書き済み・重複・一時的な進捗か？ → なら削除候補へ

### ステップ2：ドラフト作成（コピーの上でのみ）
分類に基づき、整理ドラフトを作る。書き換えの型は次を使うこと。


変更の歴史を全部並べず、次の形に圧縮する：
「現在：○○である。／ 戻し防止：△△は ×× という理由で廃止したので、再提案しない。」
※「戻し防止」の1文が重要です。これが無いと、将来のあなたが廃止したはずの方法を再提案し、行ったり来たりが再発します。ただし、戻す心配が薄い項目には無理に付けないこと。


正本ファイルの実在を確認できた項目だけ、「詳細は ○○ 参照」の1行に置き換える。実在が確認できない仕様は参照化せず、要約を残すこと。


同じ結論が複数箇所にある場合は1箇所にまとめ、他の箇所からは参照だけにする。


確定日は最小限残す。「いつ移行したか」「いつ変更したか」という移行の叙述は削る。

### ステップ3：比較レポート
本物とドラフトを比べて、次を必ず出すこと。
- Before / After の文字数・行数と削減率（実測値）
- セクション別の削減量
- Before / After の実例を6件以上（各項目の文字数つき）
- 圧縮で失われ得るニュアンスと、それへの対策（戻し防止文に残した、留保は本文に残した、など）を正直に書いた「リスク欄」
- 矛盾・判断待ちの一覧（勝手に直していないこと）

### ステップ4：検証
ドラフトの状態で、「今のデフォルトは何か？」「○○の時はどうするか？」といった確認質問に、ドラフトだけを読んで答えられるか自己テストする。答えられない項目があれば、それは削り過ぎなのでドラフトに戻して残す。

### ステップ5：採用
私が「採用して」と言った場合だけ、本物のファイルへ反映する。反映前に元のファイルのバックアップ（日付つきコピー）を必ず作ること。反映後、もう一度文字数を実測して最終報告する。

## 報告の形
最後は必ずこの形で締めること：
- 削減：○○文字 → ○○文字（−○○%）
- 主な削減方法：削除／履歴の現在形化／参照化／重複統合 のどれが主因か
- 消した項目：ある場合は件数と一覧、無い場合は「項目は消していない」と明記
- 判断待ち：残っている矛盾・未決事項の一覧
- 次に削るなら何が必要か（例：項目ごと別ファイルや別チャットへ移す判断）

## 付録：仕組み単位の小技（メモリ以外の節約）
- 話題ごとにチャットを分ける。1つの長いチャットに全部を詰めない
- 長い本文は毎回貼り直さず、ファイルに置いて参照で渡す
- 別チャットへの引き継ぎは全文転載ではなく、結論と未決事項だけの要約で渡す
- 新しい決定をしたら、古い決定に追記するのではなく古い記述を置き換える（差分を積まない）
